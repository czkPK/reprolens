# ReproLens 技术报告初稿

## 摘要

ReproLens 是一个面向开源 LLM/RAG/Agent 项目的复现就绪度审计与最小整改智能体。它将仓库中的 README、依赖、配置、prompt、模型卡、数据集卡、测试和脚本转化为可追溯的证据图，按环境、数据、模型、实验、文档和 LLM 特有风险六个维度进行评分，并生成带证据 ID 的整改计划。工具还会把 README 中的可验证声明映射到对应检查项，形成“声明—证据—缺口”矩阵，同时报告证据置信度和证据覆盖率。工具进一步提供保守的 AutoFix 机制：在 staging 副本中应用修复候选，重新审计，只保留能够提升评分的修改。

## 一、作品概述

### 1. 背景与问题

开源 AI 项目公开了代码，并不等于其他人能够复现结果。常见阻塞包括：依赖版本漂移、数据和权重缺失、prompt 与模型版本未记录、评测协议不可验证、RAG 索引不可追溯、Agent 调用过程不可审计，以及许可证和来源边界不清。

现有工具大致分为论文 artifact 评审、实验管理、环境打包和人工 checklist。它们通常要求作者主动采用，或面向论文评审，缺少面向开源仓库维护者的“诊断—整改—复测”闭环。

### 2. 目标与作品形态

ReproLens 的目标是回答三个问题：

1. 这个开源 AI 项目能否被别人复现？
2. 如果暂时不能，最关键的缺口是什么？
3. 最小修复动作是什么，修完后是否真的变好？

作品形态为 Python CLI 和静态 HTML 报告，支持 `audit`、`--autofix` 和 `--explain`。

### 3. 核心亮点

- 使用方式感知和项目类型感知的评分；
- LLM 特有复现风险检查；
- 证据 ID 和可点击证据位置；
- README 声明到检查项的证据映射与缺口追踪；
- 高/中/低证据置信度和适用检查项覆盖率；
- 保守 AutoFix 和 staging 复测；
- 开发集与 fresh holdout 双组评估；
- 无 API 时可离线输出确定性解释。

## 二、需求分析与总体方案

### 1. 需求分析

目标用户包括开源 AI 项目维护者、尝试复现论文/模型的学生和研究者、需要评估第三方仓库的实验室和教师。核心需求不是“生成一段总结”，而是获得可核验的缺口清单和可执行的整改步骤。

需求优先级：

1. 能运行、能演示；
2. 每条结论有证据；
3. 能指出最小整改动作；
4. 能复测修复效果；
5. 能接入 GitHub 协作流程。

### 2. 总体方案

```text
仓库输入
  -> 文件盘点与项目类型识别
  -> 证据抽取（README/config/prompt/model card/tests）
  -> 证据图与适用性判断
  -> README 可验证声明抽取与检查项映射
  -> 声明状态、证据置信度与覆盖率计算
  -> 多维度评分
  -> 问题清单与整改建议
  -> AutoFix 提案 + staging 复测
  -> Markdown/HTML/JSON/解释报告
```

### 3. 可行性与成本

- 仅使用 Python 标准库即可运行核心流程；
- 不要求训练大模型、不要求 GPU；
- 执行探针默认只做安全语法解析；
- 可选接入 OpenAI-compatible API，失败时自动回退离线模板。

## 三、AI 技术与开源资源选择

### 1. AI 技术作用

ReproLens 采用“确定性规则优先、LLM 可选增强”的混合方式：

1. 从非结构化 README、模型卡和数据卡中抽取声明与证据；
2. 将技术缺口转写为可理解的整改建议；
3. 在证据约束下生成诊断解释。

当前的声明识别、证据映射、事实校验、适用性判断、评分和复测均由确定性规则完成；LLM 只作为可选解释模块，不直接决定分数。这样既保证离线可运行，也避免生成式模型制造没有证据的结论。

### 2. 开源资源

当前原型使用 Python 标准库；执行环境为 Python 3.11+；可选接入 OpenAI-compatible 模型服务。正式提交前应在《开源及第三方资源使用清单》中补充所有依赖、版本、来源、许可证和关键义务。

### 3. 自主开发边界

RepoLens 的扫描器、规则、评分、AutoFix、基准和报告生成逻辑为本项目自主实现；第三方模型/服务只作为可选解释模块，不纳入核心事实判断。

## 四、设计与实现过程

### 1. 核心功能

- 项目类型识别：application、sdk、agent_framework、memory_framework、ml_project；
- 25 个复现检查项；
- 证据范围和占位符过滤；
- README 声明—证据—缺口矩阵，区分已验证、部分验证、未验证和不适用；
- 证据置信度（高/中/低/N/A）与适用检查项覆盖率；
- 安全语法探针，可选 `--help` 和 pytest collection；
- AutoFix 提案和 staging 复测；
- Markdown、HTML、JSON 和解释报告。

### 2. 关键实现

- `scanner.py`：文件盘点、证据抽取、项目类型识别；
- `rules.py`：适用性和状态判断；
- `scoring.py`：维度与总分计算；
- `autofix.py`：候选生成、逐个应用、复测和自动丢弃；
- `claims.py`：声明到检查项的映射、状态汇总、证据置信度和覆盖率；
- `llm.py`：证据约束解释和离线回退；
- `benchmark.py`：开发集、旧 holdout 和 fresh holdout 评估。

### 3. 开发过程

开发过程先实现静态规则和报告，再通过真实仓库发现误报，随后加入证据范围过滤、项目类型识别、占位符过滤和 AutoFix。进一步迭代中增加了声明—证据矩阵，并对 README 中的 HTML、Markdown 链接和营销式表述进行清洗与去重，避免把泛化描述误判为技术证据。每次修改均通过单元测试验证。

## 五、成果展示与效果验证

### 1. 成果展示

演示仓库修复前 49.1 分，AutoFix 后 68.4 分，提升 19.3 分。演示仓库共抽取 3 条可验证 README 声明，证据覆盖 16/25 个适用检查项（64.0%）。真实仓库结果：

| 仓库 | 修复前 | 修复后 |
|---|---:|---:|
| openai-python | 94.9 | 100.0 |
| smolagents | 78.8 | 85.9 |
| mem0 | 84.8 | 87.9 |
| aider | 74.8 | 81.0 |
| chat-ui | 44.1 | 62.8 |

补充真实仓库核验：对 `mem0` 的 1,837 个文件完成审计，抽取 8 条 README 技术声明，16/16 个适用检查项均有关联证据。该数字表示“有证据覆盖”，不等同于所有检查项都已通过。

### 2. 验证方法

- 3 个开发仓库，每个 14 个关键检查项；
- 旧 holdout 3 个仓库；
- fresh holdout 2 个全新仓库；
- 人工标注 + 项目类型判断；
- exact status accuracy、Precision、Recall、F1。

### 3. 验证结果

开发集（含演示 fixture）：

```text
56/56 exact status accuracy
```

旧 holdout（规则迭代后）：

```text
38/42 exact, Precision 0.917, Recall 0.786, F1 0.846
```

Fresh holdout（未参与规则调整）：

```text
26/28 exact (92.9%), Precision 1.000, Recall 0.818, F1 0.900
```

Fresh holdout（针对 RAG/Agent 证据门槛修复后复跑）：

```text
27/28 exact (96.4%), Precision 1.000, Recall 1.000, F1 1.000
```

这批复跑结果不能替代初次独立评估。当前唯一 exact 差异是 open-webui 的 LLM-03 在人工标注中为 `partial`、规则输出为 `missing`，二者在缺口检测指标中都属于正类，因此 F1 未受影响。

Final holdout（最后一批应用仓库）：

```text
28/28 exact (100.0%), Precision 1.000, Recall 1.000, F1 1.000 (post-fix validation)
```

Fresh holdout 的初次独立结果才是核心泛化证据，开发集 100% 不应作为泛化能力宣传；修复后复跑结果应明确标注为 post-fix re-evaluation。

## 六、创新性与开放价值

1. **项目类型感知的适用性判断**：SDK、框架和应用的模型/数据/实验指标不同，避免“一刀切”误报。
2. **声明—证据—缺口矩阵**：不满足于“仓库里有没有某个文件”，而是检查 README 声称的能力是否被对应检查项及证据支持，并明确列出缺口。
3. **证据置信度与覆盖率**：区分高/中/低证据强度，并给出适用检查项中有多少项存在可追溯证据，便于比较不同仓库的诊断完整度。
4. **LLM 特有复现风险本体**：模型/API 版本、prompt 版本、采样参数、tokenizer、RAG 索引、Agent trace、污染和成本。
5. **反事实最小整改**：候选文件逐个加入 staging，重新评分，只保留有益修改。
6. **证据约束解释**：LLM 只能基于已抽取证据生成解释，无证据时保留 Evidence Missing。
7. **开放基准**：开发集、旧 holdout 和 fresh holdout 的标注、规则和结果均可复现。

## 七、合规、安全与风险说明

- 本工具不执行不可信仓库代码，默认只做语法解析；
- `--execute` 只应在受信任仓库上使用；
- 第三方资源需登记许可证和关键义务；
- 生成模板中的 TODO/TBD 不算已验证证据；
- 本工具提供工程合规检查，不构成法律意见；
- LLM 输出必须人工复核，不能替代事实判断；
- 材料中不得出现学校名称、LOGO、指导教师信息。

## 八、总结与展望

ReproLens 已形成“声明验证—扫描诊断—整改—复测”的完整闭环。Fresh holdout 的初次独立评估为 92.9% exact accuracy（F1 0.900），修复后复跑为 96.4%（F1 1.000）；final holdout 修复后为 100%（F1 1.000），但该批仓库参与了最后边界修复，应作为 post-fix validation 报告。声明矩阵用于解释“项目自称能做什么”与“仓库证据是否支持”之间的差距，当前仍属于启发式映射，需要在更多仓库和人工语义标注上继续验证。

后续计划：

1. 改进项目类型和非 Python 项目支持；
2. 增加更多 fresh holdout；
3. 接入 GitHub PR 评论和复现 badge；
4. 扩展到更多模型/数据/工作流生态；
5. 建立长期维护的开源基准。
