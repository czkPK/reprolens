# AI+开源赛道国赛冲刺方案（单人版）

> 依据：附件1《AIC·AI+开源竞赛规则及作品提交要求》、附件2《AIC·AI+开源技术报告参考大纲》。
> 截止时间：2026-10-30 20:00。当前按 2026-10-19 起算，共 11 天。

## 一、项目定位

**暂定名：LicenseLens（开源合规显微镜）**

一句话：面向 AI 开源项目的“证据约束型”许可证冲突诊断与整改规划器。

不是做一个“上传依赖清单后让大模型写一段话”的套壳工具，而是：

1. 从项目清单和文件中抽取依赖、模型、数据资源；
2. 构建“资源—许可证—义务—使用方式—证据”图；
3. 用规则引擎识别真实冲突和未知风险；
4. 让大模型只在证据图允许的候选整改方案内做解释和排序；
5. 输出可复核的诊断报告、证据引用、NOTICE 草稿和整改计划；
6. 用公开基准、消融实验和用户试用证明效果。

## 二、为什么这个题目适合本赛道

- 开源许可证、依赖和模型许可是开源生态中的真实高频问题；
- 开源资源不是普通开发环境，而是作品的分析对象和核心知识来源；
- AI 的作用是解释自然语言条款、生成整改方案、降低人工审计成本，不是装饰；
- 结果可验证：许可证识别准确率、冲突 F1、证据引用准确率、整改有效性、审计耗时；
- 单人可在 11 天内完成 Python/npm 两个生态的最小可用版本；
- 容易形成代码仓库、规则包、评测集、技术文档等开放成果。

## 三、评分项对应策略

| 评分项 | 分值 | 本项目的拿分方式 |
|---|---:|---|
| 问题与场景价值 | 15 | 访谈 5-8 名开源项目维护者/开发者，整理真实审计痛点；聚焦“发布前合规检查”这一小切口 |
| 创新性与方案设计 | 20 | 使用方式感知的义务图；反事实整改规划；证据约束生成；与普通扫描器/纯 LLM 方案对比 |
| AI 与开源融合 | 20 | 以 SPDX/许可证文本/开源扫描器为证据源，LLM 负责条款解释和方案表达；完整披露版本、许可证、义务和自研边界 |
| 实现完成度与可验证效果 | 25 | 可运行 CLI + 简单 Web UI；20-30 个基准项目；冲突 F1、引用准确率、耗时和消融实验 |
| 开放成果与复用价值 | 15 | Apache-2.0 代码仓库、规则包、基准数据、评测脚本、部署文档、维护计划 |
| 材料规范与表达 | 5 | 15 页以内技术报告、3-5 分钟视频、300 字简介、资源清单、可访问链接 |

目标：不追求“功能大而全”，而是把上述证据链做完整，争取 80 分以上。

## 四、核心创新点

### 1. 使用方式感知的许可证义务图

同一依赖在“内部使用、SaaS 对外服务、二进制分发、源码分发、模型权重再分发”下的义务不同。系统把使用方式作为图中的一个节点，而不是只做静态许可证匹配。

### 2. 反事实整改规划

不仅报告“有冲突”，还枚举可执行的整改动作：

- 替换依赖；
- 隔离为独立服务；
- 开源相关修改；
- 补充 NOTICE/署名；
- 调整分发方式；
- 转人工复核。

对每个动作给出证据、影响范围和成本估计，形成最小整改集。

### 3. 证据约束的 LLM 生成

LLM 只能基于检索到的许可证条款、规则和项目事实生成解释；报告中的每个结论必须带证据 ID。增加“无证据则拒绝下结论”的机制，降低幻觉。

### 4. 可复现的评测基准

构建 20-30 个 Python/npm 项目的评测集，包含干净项目、真实冲突和受控注入冲突；提供人工标注规则、基线方法和消融脚本。

## 五、最小可行产品（MVP）范围

只做以下范围，避免 11 天失控：

- 输入：本地仓库路径或 GitHub 仓库 URL；
- 生态：Python（requirements.txt / pyproject.toml）和 npm（package.json）；
- 资源：代码依赖、模型卡/模型许可证字段、数据卡/数据许可证字段；
- 许可证：MIT、Apache-2.0、BSD-2/3-Clause、MPL-2.0、LGPL-2.1/3.0、GPL-2.0/3.0、AGPL-3.0、Unlicense、CC0、Unknown/Proprietary；
- 使用方式：internal、saas、binary-distribution、source-distribution、model-redistribution；
- 输出：graph.json、report.md、notice.md、remediation.json；
- UI：Streamlit 或轻量 Web 页面，展示冲突、证据和整改选项；
- AI：OpenAI-compatible LLM 适配器；无 API 时使用确定性模板回退，保证离线可演示。

暂不做：完整 SBOM 标准兼容、全语言支持、法律意见、自动修改上游代码、复杂多租户平台。

## 六、验证方案

### 1. 基准集

- 10 个干净项目；
- 10 个含真实或受控冲突的项目；
- 每个项目记录依赖、许可证、使用方式、期望冲突和证据。

### 2. 指标

- 许可证识别准确率；
- 冲突检测 Precision / Recall / F1；
- 整改方案有效率（人工判定是否真正消除冲突）；
- 证据引用准确率（结论是否有对应条款/规则）；
- 单项目平均审计耗时；
- 与人工审计相比的时间节省。

### 3. 对照与消融

- Baseline A：关键词/许可证字段匹配；
- Baseline B：扫描器 + 纯 LLM 解释；
- Ours：义务图 + 规则引擎 + 证据约束 LLM；
- Ablation：去掉使用方式节点、去掉证据约束、去掉整改规划，观察指标变化。

### 4. 用户试用

找 5-8 名同学或开发者，完成一次真实仓库审计任务，记录完成时间、可用性和主要问题。用户反馈只作为佐证，不伪造数据。

## 七、11 天排期

### 10月19日：定题与骨架

- 建仓库、README、LICENSE、目录结构；

- 收集 10-15 个测试项目。

- 生成资源清单和基础证据图。

### 10月22-23日：规则引擎
- 实现使用方式模型；
- 实现许可证兼容性规则；
- 输出冲突、风险等级和证据 ID。

### 10月24-25日：整改规划与 AI 解释
- 实现候选整改动作枚举和排序；
- 接入 LLM 适配器；
- 生成报告、NOTICE 草稿；

### 10月26-27日：界面与评测

- 跑 20 个基准项目；

### 10月28日：用户试用与材料

### 10月29日：视频与合规材料

- 上午完成最终检查；

## 八、材料清单

- 作品名称（<=20 字）；
- 作品简介（<=300 字，按“问题—方案—实现—效果—开放成果”写）；
- 技术报告 PDF（正文建议 <=15 页，<=10MB）；
- 演示视频 MP4（3-5 分钟，<=300MB）；
- 开源及第三方资源使用清单；
- 代码仓库/网盘链接及运行说明；
- 答辩 PPT（晋级后提交）；
- 测试记录、用户反馈、Issue/PR 链接等佐证材料；
- AI 工具使用说明（用途、环节、人工审核和验证）。

## 九、合规红线

- 所有核心代码必须为本届大赛期间真实完成；
- 第三方库、模型、数据、工具必须披露名称、版本、来源、许可证和关键义务；
- 不提交无权公开的代码、数据、API Key 或个人信息；
- 材料中不出现学校名称、学校 LOGO、指导教师信息；
- 不把“公开可访问”当成“可复制、训练、改编、再分发”；
- 不提供法律意见，只提供工程合规检查和人工复核建议；
- AI 生成的文本、代码、图片必须人工审核并说明使用环节。

## 十、风险与应对

| 风险 | 应对 |
|---|---|
| 被评委认为只是扫描器套壳 | 把义务图和整改规划作为核心，做消融实验证明增益 |
| 许可证数据不准确 | 使用 SPDX/开源扫描器 + 人工复核 + Unknown 置信度 |
| LLM 幻觉 | 证据 ID 约束、无证据拒绝结论、模板回退 |
| 11 天做不完 | 只支持 Python/npm，只做 5 种使用方式，先 CLI 后 UI |
| 没有真实用户 | 用同学/开发者小规模试用，明确样本量，不夸大 |
| 外部 API 不可用 | 提供离线确定性模式，视频演示不依赖网络 |
